# 硬件与 SDK：让代码找到正确的执行位置

[返回项目首页](../../README.md) · 对应课程 01—02

## 从一段 Python 到机器人

```text
开发电脑：编辑与查看日志
        ↓ 远程连接
HPU：Python 程序 → Galbot SDK → 感知与规划等服务
        ↓ 机器人内部通信
XCU：运动控制相关服务 → 驱动器与执行器 → 状态反馈
```

这里描述职责分工，不表示已经测量了全部服务的调度或伺服周期。HPU 与 XCU 都是机器人内部计算单元；开发电脑、跳板机和机器人不能仅凭一个 SSH 别名混为一谈。

本次学习记录中的 HPU 为 NVIDIA Jetson AGX Orin 平台，XCU 板卡信息指向芯驰昆仑 D9 系列，二者均报告 aarch64 Linux 环境。平台识别帮助选择正确 SDK 构建，但不能据此断言所有硬件能力已由当前固件启用。

## SDK、API、Python 包与动态库

SDK 是工具包，API 是调用入口，Python 包提供开发接口，`.so` 是编译后的动态库。能 `import galbot_sdk` 只证明包能被找到；`robot.init()`、状态回读和底层服务还要分别检查。

`GalbotRobot` 面向机器人状态与控制，`GalbotMotion` 面向运动学和运动规划，`GalbotNavigation` 面向定位与导航。实际类和参数以所安装的 G1 SDK 为准，不混用 G3/S1 示例。

## 开发过程中建立的习惯

1. 先确认主机、CPU 架构、Python 环境与 SDK 版本，再排查具体接口。
2. 状态反馈先行：从关节名、状态、时间戳开始，再理解动作目标。
3. 检查初始化返回值，并在异常和正常结束时释放 SDK 资源。
4. 把调用成功、命令被接受、动作结束和任务完成分别记录。

系统状态里的 WORKING_MODE 不代表正在运动；列出服务名称也不代表每个进程都处于健康状态。开发环境与机器人操作流程相互关联，但不能用一次初始化成功替代完整验证。

## 学习收获

从“运行一个示例”转向理解代码、接口、服务和硬件的边界。这是后续多模态输入和动作执行适配能够正确落地的基础。
